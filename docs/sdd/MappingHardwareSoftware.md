# 3.3 Mapping Hardware-Software

Il sistema I-Need adotta un'architettura distribuita di tipo Client-Server articolata su due nodi fisici/virtuali principali («device»): il dispositivo client dell'utente (User Client) e un singolo nodo server cloud (VPS Cloud Server). Sul lato client, l'accesso avviene da qualsiasi dispositivo (PC, tablet o smartphone) dotato di un Web Browser moderno compatibile con gli standard HTML5, CSS3 e JavaScript (RNF_I_1), garantendo la portabilità multipiattaforma (DG_7). Al primo accesso, il browser scarica dal server il bundle della Single Page Application (SPA) sviluppata in React e Bootstrap e lo esegue localmente a runtime (ineed-spa-runtime.js), istanziando il livello GUI (gli oggetti boundary del RAD), gestendo il routing client-side e validando i moduli di input per assicurare usabilità, rapidità di inserimento e chiarezza dei riscontri (DG_1, RNF_U_1, RNF_U_2).

Sul lato server, per contenere i costi di sviluppo, installazione e manutenzione (DG_8, DG_9) e rispettare il vincolo di distribuzione web (RNF_PA_1, RNF_O_1), l'intera infrastruttura risiede su un'unica istanza VPS Cloud con sistema operativo Linux, dimensionata con almeno 2 vCPU e 4 GB di RAM complessivi. Mentre durante lo sviluppo locale il frontend può essere eseguito direttamente sulla macchina host per agevolare l'hot-reloading, in produzione l'intero stack server è orchestrato tramite Docker Compose («executionEnvironment» Docker Engine) in quattro container isolati connessi attraverso una rete bridge virtuale interna dedicata (ineed-network), garantendo modularità, sicurezza ed estensibilità (DG_2, DG_6, RNF_S_1):

- Container Frontend & Reverse Proxy (nginx:alpine, porta :443): costituisce l'unico punto di ingresso (entrypoint) esposto verso la rete esterna. Ospita l'artefatto del build statico della SPA React (ineed-spa-build, composto da HTML5, CSS3/Bootstrap e bundle JS) servendolo ai browser client su protocollo sicuro HTTPS e agisce da Reverse Proxy, inoltrando le richieste indirizzate alle API REST (`/api/v1/*`) verso il container di backend sulla rete interna.
- Container Backend API (eclipse-temurin:17-jre-alpine, porta :8080): ospita l'ambiente di esecuzione Spring Boot 3 (Java 17+, Jakarta EE 10). Al suo interno è schierato l'artefatto ineed-backend.jar, che manifesta i livelli Control e Service dei sottosistemi di business (Autenticazione, Gestione richieste abitative, Gestione abitazione, Gestione matching, Gestione proposte, Gestione convivenza) e il sottosistema trasversale Interfacciamento dati persistenti (basato su Spring Data JPA / Hibernate). Il controllo degli accessi per ruolo (DG_2, RNF_A_1) e la validazione formale e temporale degli input (DG_3, RNF_A_2) sono applicati centralmente tramite Spring Security.
- Container AI Microservice (python:3.11-slim, porta :8000): esegue il framework asincrono ASGI FastAPI (Python 3.11+) che incapsula il sottosistema Modulo AI (RNF_I_2). Il servizio valida il contratto dati tramite Pydantic, calcola la similarità coseno pesata sui questionari strutturati con scikit-learn ed estrae gli embedding semantici sui testi liberi mediante sentence-transformers con il modello NLP pre-addestrato paraphrase-multilingual-MiniLM-L12-v2. Il modello opera su CPU standard senza necessità di GPU dedicate (DG_8), richiede almeno 2 GB di RAM garantiti all'ambiente e monta un Docker Volume persistente (hf_model_cache, associato alla variabile HF_HOME) per conservare su disco i circa 470 MB del modello scaricato da Hugging Face, evitando download ripetuti ai riavvii del container.
- Container Database (postgres:15-alpine, porta :5432): ospita il RDBMS PostgreSQL 15, che realizza il sottosistema Storage. Garantisce le proprietà transazionali ACID e la memorizzazione flessibile dei questionari tramite formato JSONB, assicurando la conservazione dello storico (DG_4, RNF_A_3) mediante il montaggio del Docker Volume persistente postgres_data.

La comunicazione tra il Web Browser sul dispositivo client e il container frontend-web (Nginx) avviene esclusivamente tramite protocollo HTTPS (porta :443), sia per il caricamento iniziale della SPA sia per le chiamate asincrone REST, le quali trasportano payload JSON e il token JWT nell'header per l'autenticazione stateless (DG_2, RNF_A_1). Tutte le comunicazioni applicative successive restano confinate all'interno della rete privata ineed-network: Nginx inoltra via HTTP le chiamate REST alla porta :8080 del container backend-api; i container ai-service (:8000) e db (:5432) sono inaccessibili dall'esterno e il Modulo AI non possiede alcun collegamento diretto al database (DG_2, DG_6). È il sottosistema Gestione matching su Spring Boot a pre-filtrare gli Host idonei interrogando PostgreSQL tramite driver JDBC su TCP/IP (db:5432), per poi invocare FastAPI (http://ai-service:8000) tramite una richiesta HTTP POST con payload JSON (DG_10, RNF_IN_1). Si Stima che, questa co-locazione sulla medesima istanza VPS, unita a tempi di inferenza vettoriale di 20–50 ms, consenta di restituire la graduatoria di compatibilità in meno di 1 secondo, ben al di sotto del vincolo massimo di 10 secondi (DG_5, RNF_P_1).
